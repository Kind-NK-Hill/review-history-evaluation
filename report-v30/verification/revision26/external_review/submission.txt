# 概率证明如何完成

**作者：** Shuo Deng；Kenneth W. Shum（通讯作者）。

*ProbabilityTheoryFormalization 项目评估*

**第 26 版 · 2026 年 9 月 14 日 · 结果更新至：2026 年 9 月 14 日**

<a id="abstract"></a>

## 摘要

大规模形式化项目需要完成单个证明之外的组织工作：人工智能代理必须分工求解、组合中间结果，并交付后续证明能够使用的定理。ProbabilityTheoryFormalization 为概率教材提供了这样的工作环境。本报告结合以往审核及对应代码修订，以及十一个任务组上三种工作配置的两批运行，评价项目的组织方式如何支持证明发展。[[1,4-12,24,41]](#ref-1)

实验比较遵循项目规定流程的配置A、可以查阅项目资料并调用助手的Sol作者B，以及由Astra协调Sol作者和检查服务的配置C。按统一的数学成果标准，第一批A、B各完成10/11组，C完成11/11组；第二批三者均完成11/11组。第二批原验收中的三个拒绝，分别涉及模块化接口、证明路线和可推导前提；代码与调用检查支持上述成果判断。A在两批中的求解用时中位数均高于B、C，未显示相应的任务覆盖优势。两批分别报告，任务说明与运行安排的变化用于解释比较。[[13,14,38,41,42]](#ref-13)

执行轨迹说明了哪些工作促成证明与交付。审核推动作者从原始矩推出中心矩界；助手完成的反演证明进入唯一性及后续应用。旧Scheffé交付则留下了尾部范围缺口：明确范围要求后，诊断评审一致要求修复，两次单独修复均通过验收。历史案例进一步展示从概率模型推导密度、组合相容的局部极限和修改调用者的过程；历史通过增长与后续任务组成变化也得到分别检验。[[4-11,17-20,25,27,43]](#ref-4)

第二批过程分析覆盖全部33项运行，核对4,054次实际工具调用（不含179次工具发现）及66条固定起点记录。它揭示从检索到实际证明所需的接口转换、局部成果传回的断点，并据重复出现的工具问题完成启动信息和参数预检原型。[[45,46]](#ref-45)

这些成果为改进项目提供了具体依据：审核应检查最终定理覆盖的数学范围，协作应使中间成果送达并进入证明，评价应一致接受等价实现并结合实际投入。项目的价值在这些可检查的数学工作和组织过程之间得到体现。[[21-23,40,42,43]](#ref-21)

**阅读指引。**[第1节](#section-1)介绍项目与问题，[第2节](#section-2)说明评价方法，[第3节](#section-3)报告成果和投入。[第4节](#section-4)解释任务范围、证明构造与交付中的问题，[第5节](#section-5)沿检索、修订和实际使用展开第二批过程分析，[第6节](#section-6)讨论工作流程。完整案例与历史分析见[附录R](appendix.zh-CN.md#appendix-r)，新分析方法与逐项记录见[附录S](appendix.zh-CN.md#appendix-s)。

## 1 项目如何组织与维护证明

<a id="evaluation-questions"></a>

本报告评价的对象是 ProbabilityTheoryFormalization：这个项目将教材数学转化为可以审核、供后续任务使用，并随依赖变化持续维护的形式化证明。构建成功、评审通过和教材任务完成彼此相关，却是不同的成果。报告围绕三个问题展开：

1. **哪些数学工作已经完成并可供使用？**对外提供的定理是否表达预期命题、完成要求的证明工作，并接通使用它所需的先前结果与调用代码？
2. **审核、协助与流程控制怎样影响工作？**哪些可观察的决定促成证明修复、确认既有成果、留下范围缺口或中断交付？作出决定时，执行者掌握了什么信息？
3. **关于完成和进展的判断有多可信？**哪些记录对应独立意见和可以比较的数学对象？据此得到的标签、代码检查和资源测量究竟说明什么？

以往审核与代码修订、A/B/C 任务对照分别回答这些问题的不同部分。[第 2 节](#section-2)说明两类材料的关系，不将它们合并成一个完成率。本节先解释项目文档规定的设计。实际数学工作、运行故障和维护效果的证据，来自后文具有明确时点的分析；不能仅因设计中存在某个组件，就认定它已经发挥了作用。[[1,4-12,26,34,35]](#ref-1)

<a id="section-1-1"></a>

### 1.1 从概率教材到形式化证明库

[ProbabilityTheoryFormalization](https://github.com/Kind-NK-Hill/ProbabilityTheoryFormalization) 原名 ToyApollo，研究借助人工智能将概率教材形式化。它的目标是把教材定义、命题和论证转化为 Lean 声明与证明，既表达预期数学含义，也能供后续章节使用。Lean 检查形式化证明；Mathlib 提供可用的通用数学库。[[26,34]](#ref-26)

工作从教材材料开始。提供的原文按编号小节或习题部分组织，任务计划明确待形式化的命题和可使用的先前结果，包括教材中的显式引用。程序把原文、任务要求、允许的依赖和工作草稿汇集成任务包，交给证明作者。实现时，作者可以检索允许使用的库，并编写所需的辅助引理。[[34,35]](#ref-34)

项目把数学决策与软件检查分开。人工智能代理选择证明路线、编写代码并判断数学内容是否对应原文；Python 程序准备任务、调用检查并执行接纳代码的条件；Lean 检查代码；SQLite 记录任务状态以及保留的构建和审核证据。草稿与**正式证明库**分开保存，后者是项目的官方 Lean 证明文件。项目验收将已审核的工作正式纳入该库。[[34]](#ref-34)

本报告中的**代理**是 Codex 中的一次人工智能执行会话，具有指定模型、对话上下文和工具。**作者**编写证明，**助手**提供代码或数学分析，**评审者**检查命题与证明；这些都是人工智能角色，并非本报告的人类作者。

<a id="section-1-2"></a>

### 1.2 编写、审核与接纳证明

程序把教材原文、任务要求和允许使用的先前结果交给人工智能作者；作者编写 Lean 代码，并用 Lean 检查。随后，另一位人工智能评审者判断形式化命题与证明是否满足原文和任务要求。需要纠正的工作进入修复或诊断。在已审核代码进入正式证明库之前，程序还要确认通过意见对应即将接纳的代码与材料。这是项目文档规定的流程；后文案例说明实际执行在哪些地方发生了偏离。[[34,35]](#ref-34)

Lean 与人工智能评审者回答不同问题。Lean 检查证明是否符合写出的形式化命题；**语义评审**检查命题是否表达了要求的数学内容、关键论证是否确已证明而非被当作假设，以及列出的调用代码能否正确使用结果。仅通过 Lean 检查，不能证明代码与教材含义一致。

| 阶段 | 负责者 | 产生什么结果？ |
|---|---|---|
| 准备任务 | 程序 | 汇集原文、任务要求、允许的依赖和工作草稿。 |
| 编写与检查代码 | 人工智能作者，使用检索和 Lean 工具 | 形成候选证明（当前代码版本），或得到指导下一次修改的错误信息。 |
| 审核数学内容 | 由管理流程的代理或人工操作者调用的另一位人工智能评审者 | 给出关于命题、证明责任和列出调用者的意见。 |
| 修复或澄清问题 | 人工智能作者；必要时另设只读诊断者 | 修改证明代码，或先明确命题与证明路线。 |
| 接纳已审核代码 | 程序 | 确认有效意见对应当前代码和要求，将代码纳入正式库并记录操作。 |

如果证明路线已获认可，剩余问题只是缺少引理等局部缺口，工作返回作者修复。如果出现原文不匹配、把关键结论藏进假设，或证明路线不清，则可能先需要**只读诊断**：由人工智能定位问题，再继续编写证明。诊断者不写证明，也不替代评审者。流程还禁止在语义评审失败后重提未修改的候选。第 1.4 节介绍按风险触发的**数学路线检查（Math Gate）**，它在继续编写之前检查拟定命题和证明路线。[[34]](#ref-34)

准备请求与执行请求也有区别。例如，`review-now` 准备审核材料并指出下一步动作，管理流程的代理或人工操作者仍需实际调用评审者。类似地，助手写出的代码必须从其工作区导出，传给能够使用它的角色。服务调用结束，不一定意味着作者已收到可用结果，因此案例会核对实际返回和读取的内容。[[19,34]](#ref-19)

最后，程序检查意见是否对应当前候选、辅助代码、原文和审核要求；记录称之为**评审绑定**。它防止一个版本的意见被用于批准另一个版本。纳入代码的操作失败时，原正式文件会恢复；既有正式证明在重新审核中失败时，通常保留代码并记录修复需求。这些检查维护决定与证据的对应关系，但不能保证人工智能的数学判断正确，附录R.1.2的 L3 案例展示了这一限制。[[34,39]](#ref-34)

<a id="section-1-3"></a>

### 1.3 完成证明意味着什么

下文将任务要求完成的数学工作称为**原文义务**，将调用者使用定理时必须提供的假设称为**公开前提**。把必需的中间结论写成公开前提，就将这部分证明留给了调用者。**候选**指一个具体代码版本。下面用项目以往的一次修订说明这种区别。

历史反演任务 `thm_9_5` 将区间概率与特征函数积分联系起来，说明有效的条件证明仍可能留下未完成工作。早期候选已有换元、逐点分情况、控制收敛与缩放。名为 `h_spine` 的假设提供三项分析条件：可积性、交换积分的依据和 Dirichlet 积分极限。后续候选逐步把这些职责移入证明内部。[[1]](#ref-1)

| 修订阶段 | 已有或新增的数学工作 | 仍由调用者提供的工作 |
|---|---|---|
| 初始条件证明 | 在分析条件成立时完成主论证 | 可积性、积分交换和关键极限 |
| 下一候选 | 由界与有限测度证明乘积可积 | 积分交换和极限 |
| 再下一候选 | 证明非负截断参数下的积分交换 | Dirichlet 积分极限 |
| 完整组装 | 由误差界证明极限，并组装已证成分 | 移除 `h_spine` |

非负截断参数的限制很关键。最终证明让参数趋向正无穷，因此无需最初计划的、对全部参数成立的更强辅助命题。缩小内部引理的范围，避免了不必要工作，又不削弱教材目标。相反，把必需条件留在公开 `h_spine` 前提中，就会使交付定理之外仍有实质工作。早期评审认可了中间进展，而仅看一连串未通过标签会掩盖这些进展。[[1]](#ref-1)

<a id="section-1-4"></a>

### 1.4 数学路线检查与任务调度

**父任务**负责教材原始命题。**数学路线检查（Math Gate）**检查自然语言证明路线和拟定的 Lean 命题，用于原文不匹配、把核心证明工作转为公开假设，或反复失败却没有清晰路线的情形。多数小任务不使用它。检查给出 `go` 时，可按计划继续父任务编写；给出 `stop` 时，当前计划下的普通编写暂停，须先处理所指出的问题。暂停的具体范围取决于指令，不能仅凭这个标签推断所有支持工作都被禁止。[[26,34]](#ref-26)

对多个任务，批量规划读取记录状态与依赖，区分可开始编写、需评审或路线检查、以及被上游任务阻塞的工作。它可围绕下游依赖与潜在工作冲突组织工作队列。计划确定下一步，管理流程的代理调用相应角色，每个任务仍遵循各自验收路径。因此，普通作者队列为空，可能意味着下一步该由评审者或诊断者行动，并不一定表示全部完成或必须由用户介入。[[34]](#ref-34)

<a id="section-1-5"></a>

### 1.5 库接口与验收后的维护

同一教材概念在项目和 Mathlib 中可能有不同 Lean 表示。例如，导入以项目期望定义表述的定理，并不会自动把它转为关于 Mathlib 积分的定理。对重要共用概念，文档规定先引入教材定义及基本性质，再证明连接该接口与 Mathlib 的**转换定理**，后续工作通常使用 Mathlib 形式。这针对反复出现的数学接口，并非每个局部引理都必须经历的循环。既有可运行文件应予保留，除非具体复用问题要求修复接口。[[35]](#ref-35)

依赖选择以实际使用为依据。原文提到期望，只提供数学背景，不自动要求导入项目的期望定义。导入理由应是证明所需的声明、先前定理或转换结果，并记录于依赖链中。通用库基础设施是正当支持；但若某辅助定理承载了分配任务的数学内容，评审就必须将其作为该任务证明的一部分检查，不能因其名为“桥接”便豁免。[附录R.1.1](appendix.zh-CN.md#r1-1)的方差展开比较与[附录R.3.1](appendix.zh-CN.md#r3-1)的 Gamma/Dirichlet 历史通过具体证明分析这一区别。[[35]](#ref-35)

验收并非维护的终点。定义或定理签名变化，可能要求调用者提供不同参数或假设。任务和依赖记录识别受影响工作，构建与评审检查修改后的接口及其使用。SQLite 为底层证据保留可重建索引，并区分早期通过意见、对当前代码及支持的覆盖，以及仍需处理的工作候选。发生变化后，必须重新检查相关覆盖，而不只是保留通过标签。[附录R.3.2](appendix.zh-CN.md#r3-2)的全变差修复具体展示了这一义务：原文的概率测度条件必须同时落实到定义与调用者。[[7,34]](#ref-7)

<a id="section-2"></a>

## 2 评价证据与方法

两类证据回答[第 1 节](#evaluation-questions)提出的项目问题。**以往审核及对应代码修订**展示项目发展中证明责任、对外命题、共享辅助代码和调用者怎样变化；还用于辨认独立判断、确认数学目标是否可比、检验失败后追踪中的选择效应，并直接检查保存代码。[附录R.3](appendix.zh-CN.md#r3)及附录 [C](appendix.zh-CN.md#appendix-c)、[D](appendix.zh-CN.md#appendix-d)、[L](appendix.zh-CN.md#appendix-l)分别给出这些分析自身的问题、方法和发现。[[1,4-11,32]](#ref-1)

**十一个任务组的 A/B/C 对照**，将项目规定的流程与两种替代组织方式放在相同任务上比较。交付和资源记录说明各次实际执行产出了什么、消耗了多少；执行记录解释具体修复、漏检和中断。[第 2.1–2.4 节](#section-2-1)说明实验设置，[第 3–5 节](#section-3)报告发现。实验不能替代关于项目维护的历史证据，历史中的通过也不计入实验成功数。[[12-14,24,31,38]](#ref-12)

**轨迹分析在两类材料中连接实际工作与结果。**它追踪待完成的数学责任、收到的意见或指令、可观察的回应，以及随后被评价的代码与交付。历史记录和实验日志的详细程度不同；无法据记录确认的接收、使用或动机，不作补推。[第 2.5 节](#section-2-5)说明重建方法与覆盖范围。本报告的总体评价问题、下文所述原实验动机，以及后来开展的回顾分析分别交代。[[9,10,17-20,24,25,27,29,40]](#ref-9)

<a id="section-2-1"></a>

### 2.1 为什么比较 A、B、C？

完成概率证明既要写代码，也要决定何时检查、怎样回应错误、何时提交。项目为这些决定规定了审核与修复步骤。实验考察这些安排能否帮助代理完整交付，并与两种自主组织方式比较：由 Sol 主作者自行安排，或由 Astra 协调 Sol 作者和检查服务。三者处理相同任务组。B、C 是实验中的替代方案，不是项目后续的生产阶段。比较指标包括完成情况、求解经过时间和记录到的模型活动。[[12,14]](#ref-12)

**A 按项目规定的流程工作。**Sol 作者选择证明路线、检索库和修改代码，其他 Sol 会话承担检查。项目流程规定审核与修复条件，以及代码进入正式库之前需要满足的要求。

**B 由 Sol 主作者自行安排工作。**它收到一般工作建议，可以查阅项目的流程和审核资料，也可以请求其他 Sol 会话协助编写或复核。主作者决定怎样使用这些资源、是否检查，以及何时提交；实验没有要求它走完 A 的规定流程。

**C 由 Astra 安排 Sol 的工作。**Astra 协调者可以读取任务和代码，给 Sol 作者具体的数学建议或修改指令，再根据作者的结果和检查意见决定下一步。它知道可用服务的用途和调用方法，但没有获得内部检查指令全文。它自行选择是否调用检查；检查者仍按后台预设要求工作。[[12,18,38]](#ref-12)

| 配置 | 谁安排工作？ | 可以获得哪些帮助？ | 检查怎样安排？ |
|---|---|---|---|
| A：规定流程 | Sol 作者在项目流程约束下工作 | 按角色提供项目指令和人工智能检查 | 流程规定审核与修复条件 |
| B：Sol 自主组织 | Sol 主作者 | 项目参考资料；其他 Sol 作者或复核会话 | 主作者决定是否调用及如何跟进 |
| C：Astra 协调 | Astra 协调者，Sol 作者实现证明 | 工具说明；Sol 作者和固定检查服务；返回意见 | 协调者决定是否调用及如何跟进 |

这些角色都是人工智能代理。Sol、Astra 分别指记录中的 `gpt-5.6-sol` 和 `gpt-6-astra` 配置。证明作者和检查角色使用 Sol，只有 C 的协调者使用 Astra；均采用 medium 推理强度设置。medium 表示推理设置，不是模型能力等级。B 是能够查阅文档并请求协助的自主配置；实验没有另设只获得题目、既无项目资料也无其他代理帮助的最简基线。C 同时改变决策模型、角色结构和信息权限，因此比较对象是三套完整安排。[[12,18,31]](#ref-12)

在本次对照中，轨迹分析考察规定的检查或自选检查何时找出了缺失的数学工作、何时错误放行，协调者怎样使用返回反馈，以及工作为什么继续或停止。对同一任务，先核查各配置是否遇到相同困难，再追踪谁指出问题、意见是否送达、代码如何变化。附录R.1–R.2据这些过程解释实际安排的具体优点与失败，不把完成数量当作审核质量的直接度量。

### 2.2 代理获得什么信息，怎样完成一次任务？

每组获得教材原文、任务要求、允许使用的数学库和指定的先前结果。代理需要提交定理声明、证明、必要的辅助代码及说明，解释它们如何完成任务。本报告将这套代码和说明称为**交付**。[[12]](#ref-12)

一次运行由**外层实验执行代理**启动和管理，它也是 Codex 中的人工智能代理。A、B 或 C 在提供的材料和时间额度内组织求解，随后交付成果，由新的评审会话按共同标准评价。内部审核通过、代码进入项目正式库和实验评价通过是分别记录的事件，第 2.4 节说明评分方法。

外层实验执行代理与 C 的 Astra 协调者分工不同：前者管理实验运行，后者在 C 内部安排证明工作。外层代理可以干预任何一组，例如停止后续活动。第 2.3 节和具体案例分别说明这些操作及其影响。[[31,38,39]](#ref-31)

工作资料具有不同作用。**流程资料**说明项目怎样组织编写、审核和修复；**审核资料**说明检查时关注哪些问题，例如是否增加了题目没有要求的假设、是否完整证明了所需结论。**工具说明**解释可以请求什么服务以及怎样调用；**检查反馈**则指出本次代码存在什么问题，或给出通过意见。

A 的作者与检查者分别收到相应角色的项目指令。B 的初始提示给出规划、检索、检查和按需求助等一般建议，项目流程与审核资料供它主动查阅；文档可用不等于每次运行都读过。C 的协调者可以读取公开任务、代码和反馈，但未获得一般审核与数学检查的内部指令全文。反馈仍可能让它了解部分检查标准。因此，C 自主决定怎样组织工作；任务要求和后台检查要求并不由协调者任意制定。[[38,39]](#ref-38)

B 的主作者能够直接操作终端、编辑代码，也可以编写请求交给其他 Sol 会话。C 将协调和执行分开：Astra 通过工具读代码、指派作者并请求检查，Sol 作者操作终端和修改代码。协调者可以给出具体证明建议，但不能通过固定检查工具改写检查者的内部指令。两组的内部复核均属于求解过程，之后还要接受实验的共同评价。[[38,39]](#ref-38)

研究选择十一个任务组，覆盖不同数学工作与组织问题。部分任务组要求相互连接的多个结果。L、M、H 是计划时的工作量分组，下面列出具体题目，后文用这些标识定位案例。[[12,31]](#ref-12)

| 组别 | 数学任务 |
|---|---|
| L1 | 构造新息，并证明其部分和形成鞅 |
| L2 | 教材11.4方差可加性与11.5弱大数定律 |
| L3 | Scheffé 引理、密度收敛及相关分布结论 |
| L4 | 全变差公式与分布计算 |
| L5 | 构造最大耦合 |
| L6 | 单传感器与双传感器线性最小均方误差 |
| L7 | 向量按坐标收敛与连续映射 |
| M1 | 停止过程与停止期望 |
| M2 | 四阶矩条件下的强大数定律 |

| H1 | 特征函数反演、唯一性及两个应用 |

### 2.3 哪些运行进入比较，执行条件有哪些变化？

B、C 的早期试跑暴露过两类执行问题：已经承诺提供的资料或工具未实际提供；检查意见或助手代码已经生成，却未能正常返回给负责下一步决策的代理。执行程序随后得到修复。由于这些问题影响代理能够使用的信息，主要比较与早期试跑分开报告。[[31,38]](#ref-31)

本报告将从启动求解开始、包含作者修改、求助、检查和同一计时下继续工作的全过程计为**一次求解运行**。第一批开发记录中共有 41 次；原主表为每个任务组选取 A、B、C 各一次交付，共 33 项。A 包含九次较早运行和 H1、M3 两次较后运行；B、C 各采用十一次执行程序修复后的运行。早期 B、C 试跑用于分析故障及反馈使用。各次具体执行仍须检查，程序修复本身不能保证之后所有调用都成功。[[12,13,31]](#ref-12)

同一次运行可能留下多次交付，汇总时按记录顺序优先保留已有共同评价的完整交付，没有完整交付时保留已有共同评价的首份交付。由此，A-H1 在原计时内继续完成的成果计入该次运行。该规则由事后汇总程序确认，尚未找到运行前固定它的记录。[附录 N.1](appendix.zh-CN.md#n1)保留精确选择步骤与运行对应表。[[31]](#ref-31)

选入共同评价的十一个任务组中，三组的教材原文和任务单一致；允许使用的先前结果清单也一致，唯一例外是 A-L7 还列出一个没有实现的连续映射目标。求解期间的资料、工具和干预则有下列具体差别。[[31]](#ref-31)

| 执行差别 | 实际发生了什么？ | 如何解释结果？ |
|---|---|---|
| B 的资料和工具 | 早期试跑未获得部分承诺的能力，后续补齐并验证可用 | 主比较采用补齐后的 B；早期试跑另列 |
| B、C 的结果传递 | 后续程序修复了部分检查意见或助手代码无法返回的问题 | 分析以决策者实际收到的内容为依据 |
| 任务附加提示 | B 的最终参考包移除了 L4 必须使用指定接口的约束，以及 M3/H1 模块名提示；A-L4 实际收到过相关条件指令 | 按具体提示报告差别；尚未量化这些提示的影响 |
| A-L7 的外层中止 | 尚余约 61 分钟时，外层禁止继续编辑、求助和新审核 | 原交付反映提前中止；恢复后的成果单列 |

C 扩展到不同任务时，也调整了允许启动的题目和时间额度设置；选入的 C 运行共用核心后台与角色提示内容。[附录 O.1](appendix.zh-CN.md#o1)具体说明接口约束、组织线索、实际暴露情况，以及实现共同性的范围。这里保留影响解释的实际条件，后文结合代码和反馈判断其作用。[[38]](#ref-38)

9 月 13 日的 A-L7 续作在封存工作状态的副本上恢复原作者，并明确允许交付合理修正后的命题。续作交付计入第3.1节的完成结果，追加时间计入第3.2节的累计用时。原轮次记录与指标同时保留；此前41次运行的历史清单不因这次续作而改写。附录R.2.6说明续作条件与证明变化。[[39]](#ref-39)

第二批按预先登记顺序完成同样十一组的A、B、C各一次运行，共33项。教材、给定数学库、模型型号、推理设置和任务额度保持一致；五组任务追加了验收说明，A的部分复审与回修安排、部分参考资料以及客户端和工具调用方式也有调整。第一批已按修正标准重评，评分修正本身不是运行条件变化；提前给作者的说明则改变了求解输入。两批因此分别报告。具体差分见[附录Q.1](appendix.zh-CN.md#q1)。[[41]](#ref-41)

### 2.4 完成证据与提交后的共同评估

判定实验任务完成，需要检查交付覆盖了哪些数学要求，不能仅凭命令成功或作者决定提交。Lean 检查实际写出的命题；语义评审判断它与任务要求的关系；项目在接纳代码前检查意见的对应关系和接纳资格。任务对照另由提交后的独立评审者，按下述共同程序作出报告使用的完成判断。因此，以下几类证据回答不同问题：

| 证据 | 回答的问题 |
|---|---|
| 构建 | 代码能否在记录的环境中通过检查？ |
| 语义评审 | 评审者是否认为命题与证明满足原文义务？ |
| 绑定与生产验收 | 项目是否针对所需代码及当前评审依据应用了合格意见？ |
| 提交后的共同评估 | 实验交付是否满足本次实验采用的标准？ |

第3节采用两批一致的数学成果标准：交付覆盖完整目标，允许数学等价路线及可组合接口；可从原题设和允许库直接推出的冗余参数，通过独立调用检查确认。指定路线是否遵守另记。原共同评估提供已有证据，后续复核纠正不一致判定，原意见保留。以下介绍原评审程序；本版对66项的逐项复核规则与三项调整见[附录Q.2](appendix.zh-CN.md#q2)。历史材料保持各自时点的含义，实验成果与纳入生产库仍分别记录。[[13,26,42]](#ref-13)

**共同评估**是本次实验在提交后进行的评价，有别于求解过程中的帮助与内部评审，也有别于生产验收。原始端点评估程序对原文、任务、候选、允许的上游材料及记录的技术检查，请求两份新的只读语义意见。评估者请求中不提供配置元数据。两票同为通过或失败即形成裁决；两票均无法判断则维持未决；票决不同最多触发一名新裁决者，读取相同材料和两份意见，解决实质分歧，而非按置信度选票。原始、一致性及定向端点调用均使用记录中的 Sol 中等推理配置。[[30]](#ref-30)；[附录 N.6](appendix.zh-CN.md#n6)

任务组判定针对要求的完整交付。仅通过坐标收敛定理，不等于完成含两个目标的向量收敛组；对明确标为局部成果的评审，只评价该成果，不替代缺失的任务。结果格式错误也与数学问题分开处理。在表示定理案例中，评审者写出通过意见，却在必须填写数字的置信度位置填入对象；评估软件据此记录未决的执行结果，流程随后进入裁决。[[22,28,30]](#ref-22)

随后重新评估方差展开、Scheffé 引理及 Cauchy 范围中的解释不一致。每个候选在规定解读下分别获得初始意见。义务上的分歧、无效结果，或对各候选对应行为的不一致处理，都可能触发必要裁决。这些裁决者可以看到新的初始意见和跨候选一致性摘要，对这部分后续证据并不设盲。反演组在六份初审后，对称补充了原始提交说明，因为匿名、仅看代码的视角不足以判断文档要求。[[23,30]](#ref-23)

9 月 12 日比较的修正验收明确采用四项解释：方差可加性允许通用展开路线；Scheffé 引理采用任务中的尾部表述；Cauchy 任务以教材的标准 Cauchy 核心为准；连续映射任务允许对不足的假设作合理且已披露的修正。9 月 12 日 09:22，已有意见被复用，可确定的格式不匹配被修复，并按这些标准重新合成结果。连续映射的两份追加意见此前已在 05:17 的补充中取得。这是事后的标准修正，不是求解者新增证明。[附录R.1](appendix.zh-CN.md#r1)说明数学依据并保留原判定。[[13,15,22,30]](#ref-13)

[附录 N.6](appendix.zh-CN.md#n6)说明各阶段规则、评估输入和设盲限制。这里的**独立**指有记录的评审会话与角色分离；裁决者会有意接收先前证据，同一模型使用不同会话也不能证明模型错误相互独立。

### 2.5 如何追踪信息、决策与证明变化

轨迹分析要解释任务怎样走到最终结果。对每个重点案例，我们连接数学要求、作者或协调者实际收到的信息、下一步行动、定理声明与证明的变化，以及最终接受评价的版本。历史案例也沿着这些问题追踪审核和代码修订，并额外检查前后记录中的数学目标是否可比。[[8-11,17-20,25,27,29]](#ref-8)

核心比较是关键事件前后的实际工作。审核可能促成新推导，也可能支持提交未修改的代码，或根本未能送达作者。协助者可能写出了有效证明，但成果没有进入最终交付。我们查看工具返回和阅读记录，对比代码，并追踪复用结果的实际调用，以区分这些过程。无法恢复的环节保持未确认；已有事件仍可解释其前后的工作。[附录R.2](appendix.zh-CN.md#r2)呈现这些发现。[[17-20,24,25,27,40]](#ref-17)

案例来自已经调查的修复、协助与执行问题，支持对具体过程的解释。日志提取覆盖全部记录中的求解运行，但判断反馈是否正确、是否被采用，还需要进一步阅读。另一次专项分析对索引中的 127 项内部服务中的六项采用了同一套详细标准；其他案例各有记录明确的考察范围。这些材料尚不能给出全体正确反馈采用率或数学修复率。[附录 N.4](appendix.zh-CN.md#n4)说明分析单位与覆盖，[G.18](appendix.zh-CN.md#g18)呈现六项检查，[M.2](appendix.zh-CN.md#m2)说明日志处理规则。[[16,24]](#ref-16)

另对A、B的两份旧L3代码，分别在原审核指令和明确尾部要求下各进行三次新评审，共12次；再对两份旧代码分别发起一次明确要求下的修复。诊断使用固定代码，修复使用另行冻结的指令，均与33项主运行分开。附录R.1.6报告结果，完整输入和判定见[附录Q.4](appendix.zh-CN.md#q4)。[[43]](#ref-43)

第二批另按统一起点规则调查全部33项运行：每项取最早的数学检索及最早的证明或接口诊断，连接后续行动、局部成果与最终源码，共66条记录。25项运行的两个起点涉及同一需要，分别汇总。第5章报告这项过程分析，选择规则、逐项表及复核见[附录S](appendix.zh-CN.md#appendix-s)。[[45]](#ref-45)

## 4 从完成结果看证明工作中的问题

第3章显示，三种配置在第二批都完成了全部任务，所用时间却不同。理解这些结果，需要进一步看代理在证明中处理了什么。本章按工作推进的顺序介绍八类问题，并用已有案例说明它们怎样影响交付；第5章再对第二批的检索、诊断和代码使用作统一分析。

<a id="section-4-1"></a>

### 4.1 明确目标范围，并检查交付是否覆盖它

**确定目标范围。**教材表述、任务说明和库定理的前提需要逐一对应。作者要明确哪些输入属于任务范围，哪些性质应在证明中推出，以及哪些推广属于额外工作。这决定了最后需要交付什么。[附录R.1](appendix.zh-CN.md#r1)保留各项判定的数学依据。

第一批Scheffé引理任务（L3）说明了范围差别为什么会影响完成结果。旧A、B交付要求函数序列的每一项都可积；任务还要求处理从某一项开始可积的序列。后一种输入允许前面有限项不可积，因此不能直接交给旧定理。要完成这部分工作，作者需要截取可积的尾部，在尾部应用论证，再把极限结论接回原序列。这里缺少的是覆盖任务输入的证明步骤。[附录R.1.2](appendix.zh-CN.md#r1-2)

**检查最终交付。**评审者也需要核对上述范围。对两份固定旧代码进行的新评审中，原指令下A的三份意见都通过，B的两份通过；明确要求核查尾部范围后，两份代码各自的三份意见都要求修复。B在原指令下的三份意见其实都讨论了范围问题，其中两份仍把它当作可选推广。识别问题和把问题列为验收要求，是这组记录中的两个不同决定。

随后另行开展的两次定向修复均补齐了尾部接口并通过共同验收。修复说明这两个缺口能够在明确要求下解决；固定代码的诊断则说明审核注意到了什么、又要求完成什么。完整的十二次意见、修复指令和代码变化见[附录R.1.6](appendix.zh-CN.md#r1-6)及[Q.4](appendix.zh-CN.md#q4)。这些单独修复保留自己的结果，第一批原交付仍按当时的代码计分。[[43]](#ref-43)

<a id="section-4-2"></a>

### 4.2 寻找数学工具，并把它们组成证明

**查找资料。**作者可能知道数学上需要的结论，却不知道库中的名称和位置。搜索关键词、阅读源码和查询声明类型，可以找到候选；返回空结果或名称不存在时，还需要调整查询。这里的进展首先是找到了什么资料。[附录R.2.1](appendix.zh-CN.md#r2-1)

**连接已有声明。**候选定理的输入、输出需要与当前目标对应。指标起点、函数表示、类型转换及可测性、可积性前提，都可能要求额外处理。两条表达相同数学关系的声明，也可能需要一段转换证明才能接起来。第5.2节将具体展示这种转换。

**补齐数学推导。**现成结果只能完成部分工作时，作者需要建立辅助引理，再完成组合。第一批四阶矩强大数定律任务（A-M2）中，原始四阶矩条件与后续证明所需的中心矩界之间就存在这一步。作者根据反馈补上推导，把原来留给调用者的条件移入证明。案例的意义在于哪项数学工作实际得到补齐。[附录R.2.2](appendix.zh-CN.md#r2-2)给出前后代码与检查记录。[[25]](#ref-25)

**判断并落实反馈。**构建返回定位形式化代码中的问题，数学评审检查任务要求与证明内容。作者需要结合当前版本判断意见，再决定修改代码、补查资料、调整路线或请求协助。分析时把这几步连接起来，才能看清一次反馈之后发生了什么。[附录R.2.8](appendix.zh-CN.md#r2-8)

<a id="section-4-3"></a>

### 4.3 传回成果，并让后续工作继续

**交付协助成果。**助手可以完成一个引理，也可以实现整个任务组。负责后续工作的作者需要收到可读代码、整合它，并检查实际调用。第一批反演任务（H1）的支持结果被唯一性证明和后续应用使用，说明协助能够接入数学工作；另一些协助已有产出，却未确认进入最终证明。判断采用，需要查看返回内容、代码变化和调用位置。[附录R.2.3–R.2.5](appendix.zh-CN.md#r2-3)保留这些对照。[[17-19,28]](#ref-17)

**恢复执行。**文件访问、命令入口、结果传递或外层停止指令，也会阻塞证明工作。代理需要根据实际返回找到可以继续的动作。第一批A-L7在获准续作后完成了审核和交付，其过程同时涉及命题修正与执行权限恢复；记录必须保留这两个条件，才能解释最终结果。[附录R.2.6](appendix.zh-CN.md#r2-6)给出续作前后的状态。[[39]](#ref-39)

这些问题把最终成果与中间工作连接起来：资料要适用于当前目标，局部证明要传到使用者手中，交付还要覆盖要求的范围。下一章沿这些连接读取第二批记录，先报告统一追踪的结果，再展开其中的具体过程。

<a id="section-5"></a>

## 5 从检索、修订到实际使用

第二批33项运行全部通过共同数学验收。相同的完成结果之下，代理仍经历了检索、试用、修改和协作。本章追踪这些工作怎样连接到最终证明，回答三个问题：找到的资料怎样变得可用，检查反馈之后发生了什么，局部成果怎样进入最终交付。

<a id="section-5-1"></a>

### 5.1 沿同一证明需要追踪后续工作

分析从11个任务组三种配置的完整工具记录开始。去重并配对后，共有4,054次实际工具调用，另有179次工具发现。记录保留调用的输入和返回；一次调用可能同时搜索、修改和检查，因而还需要阅读内容，确认它处理的具体证明需要。[[45]](#ref-45)

每项运行选择两个起点：首次主动查找数学名称、类型或源码，以及首次读入源文件后的证明或接口诊断。随后沿同一需要查找后续查询、代码修改和检查结果，并核对最终源码。例如，从一次定理检索开始，后续记录要说明候选是否适用、作者补了什么连接，以及相关结果最后是否被使用。

| 观察材料 | 覆盖 | 本章用它回答什么 |
|---|---:|---|
| 实际工具调用 | 4,054 | 哪些操作和返回实际发生，工具问题分布在哪里 |
| 首次数学检索及其后续过程 | 33 | 找到资料后怎样推进证明，与最终源码有何联系 |
| 首次证明或接口诊断及其后续过程 | 33 | 检查暴露了什么，后续如何处理同一需要 |

两类起点共形成66条记录；25项运行的两个起点涉及同一需要，因此两类分别汇总。这个选择规则覆盖了每项运行的早期工作，后面新出现的其他检索和修复没有全部逐段标注。以下数量描述所选过程；发现相关声明、局部检查通过和最终源码采用分别记录。具体选择规则及复核分工见[附录S.1–S.3](appendix.zh-CN.md#s1)。

<a id="section-5-2"></a>

### 5.2 找到相关定理以后，还需要哪些工作？

33条检索记录与最终源码的联系如下。统计沿首次检索所处理的需要向后追踪，包括后续查找和修改；它反映这一段工作的去向，不能解释为第一次查询就命中的比例。

| 所跟踪过程与最终源码的联系 | 记录数 |
|---|---:|
| 至少一项相关声明被显式使用 | 29 |
| 相关实现或部分成果保留 | 2 |
| 首位协作者的成果被后续交付替代 | 1 |
| 尚未确认联系 | 1 |
| 合计 | 33 |

这张表先确认检索与交付之间的连接，实际代码则解释连接是怎样建立的。第二批Skorokhod表示任务B-M3中的分位数构造提供了一个具体过程。作者找到了分布函数的极限、单调性和右连续性工具，但教材定义与库定义采用不同的函数表示。数学上相关的结论已经找到，直接替换表达式仍未通过类型检查。

| 过程 | 记录中的行动或结果 |
|---|---|
| 检索与试用 | 找到相关分布函数工具，并尝试用于当前定义 |
| 检查反馈 | 直接改写未通过，当前函数表示与所用声明不能直接衔接 |
| 修改证明 | 先逐点证明两种定义相等，再得到函数等式，用它改写目标 |
| 核对成果 | 支持文件通过检查，最终源码保留了这段转换 |

这段过程中的修改有明确对象：把两种表示连接起来，已有定理才能作用于当前目标。若只读检索结果，会漏掉应用前需要完成的证明；若只读最后的通过意见，又会看不到这一转换为何出现。工具返回、修改后的代码和最终调用共同解释了该段工作的进展。[附录S.2–S.3](appendix.zh-CN.md#s2)保存逐项证据。

第二批停止过程任务B-M1展示了这种工作怎样跨角色发生。审核者搜索后返回停止过程接口及合成鞅的具体路线。作者实际收到这些内容，随后复读源码、补齐定义连接并修正索引转换，最终证明调用了这一路线。这里可以同时确认资料送达和后续使用；中间的定义与索引处理，则说明作者仍需完成哪些适配工作。

这些案例说明，检索之后的应用工作值得单独检查。当前记录足以说明上述连接怎样完成；所选过程的记录终点深度不同，尚不能据此比较三种配置的总体恢复率或恢复速度。

<a id="section-5-3"></a>

### 5.3 诊断之后，原来的问题发生了什么变化？

首次证明或接口诊断中，19项来自实际实现，14项来自临时声明查询或局部试验。区分这两种场景，有助于读懂返回内容。正在构造的证明报错时，需要检查相应目标如何修复；试探库中名称时，同一个返回可能同时提供可用声明的类型，以及其他名称不存在的信息。

因此，一段处理过程需要围绕具体对象阅读。在B-M3中，修改前后对应同一个函数表示问题，后续检查和源码能够确认这一问题已解决。在第二批线性最小均方误差任务B-L6中，一次平方积分试验则未见解决证据，整项任务后来通过共同验收。整体完成与该次试验的结果分别记录，才保留了中间工作的实际情况。

这也解释了第3.3节报错计数与本章分析之间的关系。报错分布说明哪些运行产生过相关反馈；阅读后续行动才能说明代理如何处理它。一个返回中有多少报错、一个运行最终是否通过，都无法单独回答其中某项证明需要怎样得到解决。完整的逐项追踪表见[附录S.2](appendix.zh-CN.md#s2)。

<a id="section-5-4"></a>

### 5.4 局部检查通过的代码怎样到达作者？

跨角色工作还有一个独立环节：支持角色工作区里的证明需要实际传回。第二批A-M2和A-M3中，首位支持角色已经得到通过局部检查的代码，但返回补丁为空。作者随后读取自己的文件时，看到的仍是任务输入。局部证明已有进展，作者能够继续使用的文件却没有相应变化。

| 检查位置 | A-M2与A-M3中观察到的状态 |
|---|---|
| 支持角色的工作区 | 已有通过局部检查的代码 |
| 首次返回 | 补丁为空 |
| 作者随后读取的文件 | 仍是任务输入 |
| 后续工作 | 重新委派和交付后，非空补丁进入作者工作区 |

这条记录把断点定位在成果传递上。最终运行通过，并不能补出第一次空返回中不存在的代码；后续交付应按自己的来源记录。B-M1的返回内容和最终调用则建立了实际使用的连接。两类过程共同说明，核对协作需要同时查看协助方的成果、实际返回和使用方的文件。[附录S.3](appendix.zh-CN.md#s3)提供补丁内容、文件对应关系及源码引用。

协助是否有用，因而有可以检查的具体依据：作者收到了哪些内容，哪些内容进入后续证明。当前案例确定了这些位置上的成功连接或断点，没有测量协助相比独自求解节省了多少时间。

<a id="section-5-5"></a>

### 5.5 将工具问题转化为可检验的改进

前几节从具体证明需要追踪工作。本节回到全部工具调用，检查跨运行出现的执行问题。共有173次调用出现命令查找失败，其中49次的外层退出码仍为0。这里依据命令的实际返回识别问题，外层状态不足以完整描述内部执行。

其中，对`apply_patch`的调用有66次查找失败，分布在全部33项运行和64个会话。这种跨会话出现的同类问题，提示可以在开始工作时说明实际可用的命令入口。命令查找失败还可能来自名称或搜索路径问题，具体类别和来源见[附录S.4](appendix.zh-CN.md#s4)。

据此完成了启动工具信息卡；另针对工具的参数拒绝实现了参数预检。两个原型各自解决一个明确问题，并分别进行了功能验证。[[46]](#ref-46)

| 原型 | 要解决的问题 | 已完成的验证 |
|---|---|---|
| 启动工具信息卡 | 让作者在工作开始时看到实际可用的工具入口 | 在隔离容器中核对默认入口及搜索路径变化，确认信息卡能区分这些状态 |
| 参数预检 | 在请求执行前识别格式或取值不合规的参数 | 静态回放两个工具的3,896次输入，识别9次原有拒绝，接受3,887次合法参数，与原程序的参数条件一致 |

这些结果确认了原型功能。参数合法仍可能在执行时遇到问题；信息正确提供后，代理是否据此调整行动，也需要实际观察。后续拟议对照只改变启动信息卡，保持任务、起点、预算、角色和数学标准一致；参数预检作为两组共同的离线检查器。该模型效果对照尚未运行。

本章由记录得到的结果是具体的：检索后的表示转换把资料接入了证明；空补丁使局部成果与作者文件暂时脱节；跨会话的命令问题提供了可实施的改进对象。这些发现进一步说明评价工作流程时，需要把最终数学成果与产生它的过程连接起来。

<a id="section-6"></a>

## 6 讨论：怎样组织数学工作

前面的结果从三个角度解释项目：第3章比较交付和投入，第4章说明任务范围与工作类型，第5章追踪资料、反馈和代码怎样进入证明。本节据此讨论审核与协作的作用，以及这些记录能为流程设计提供什么依据。

<a id="section-6-1"></a>

### 6.1 完成结果与投入需要一起阅读

三种配置都交付了停时期望、四阶矩强大数定律、Skorokhod表示，以及从反演到唯一性的应用链。这些任务包含辅助引理、结果组合和调用适配。两批的共同评价进一步显示，第一批C覆盖全部任务，A、B各留下一个L3缺口；第二批三者均完整交付。

A在两批中的求解时间中位数均较高，未显示相应的覆盖优势。这为检查规定流程的投入提供了依据。同题结果还说明，中位数较低的配置并非每题都更快：第二批B、C的领先任务互有不同。第3章的逐项结果和完整计时保留了这种差异。两批的部分提示和运行安排有变化，配置也同时涉及模型和组织差别，现有结果不能确定某个单独机制的提速效果。[[41,42]](#ref-41)

<a id="section-6-2"></a>

### 6.2 审核和协作的作用可以落实到具体工作

审核的作用可以通过缺失工作的变化检查。第一批A-M2在反馈之后补齐中心矩界；旧L3诊断则说明，同一范围问题可能被遗漏，也可能被注意到却未列为必要修复。明确要求下完成的两份修复进一步给出代码证据。第4.1–4.2节中的这些过程，将意见内容、验收决定和实际修订联系起来。[[25,43]](#ref-25)

协作的作用还取决于传递和整合。第二批B-M1能够连接审核者返回的资料、作者的定义与索引处理，以及最终调用。A-M2、A-M3的空补丁则表明，支持角色的局部检查通过后，作者仍可能没有收到代码。第5.2和5.4节的对照使问题所在的环节可以辨认。[[45]](#ref-45)

这两类观察对应清楚的设计重点：审核要检查任务真正要求的范围；协助要提供作者能够继续使用的内容。增加审核次数或启动更多助手是否改善整体表现，还需要在相同条件下比较实际结果与投入。

<a id="section-6-3"></a>

### 6.3 历史进展与本次过程分析怎样互补

项目历史记录跨越多个代码版本，补充了单次运行之外的数学进展。已有调查追踪了从归一化Gamma变量推导密度、组合局部极限，以及把一般中心极限定理接入具体应用的工作。详细推导和调用者修改保留于[附录R.3.1–R.3.3](appendix.zh-CN.md#r3-1)。它们解释证明库怎样逐步获得可使用的结果。[[4-8]](#ref-4)

历史统计还检查了怎样解释通过数量的变化。在要求前后数学目标可比、意见对应正确代码后，仍能观察到通过增加；但精读案例只解释了其中一部分。后续修订通过比例下降时，追踪到的任务组成也变了，留下的任务在最初一步就较少成功。因此，比例下降尚不足以证明继续修订的收益递减。对照与计算见[附录R.3.5–R.3.6](appendix.zh-CN.md#r3-5)。[[10,32]](#ref-10)

本次第二批分析提供了另一种覆盖：对每项运行的两个规定起点，用同一规则追踪后续过程。它补充了跨运行的检索与采用记录，同时保留第5章展示的具体代码变化。历史案例解释较长的证明发展，统一起点分析说明选定过程在各次运行中怎样出现；二者的计数各自保留对应范围。

<a id="section-6-4"></a>

### 6.4 从观察到的问题形成改进

已经得到支持的改进对象包括：让审核明确覆盖公开定理的必要范围，让协助返回可读且可使用的代码，以及在开始工作时提供准确的工具入口信息。前两项对应第4–5章中的实际交付过程，后一项已有功能原型与验证。评价这些改动时，仍需使用共同数学成果标准，并保留求解中的等待、修复和协助投入。

本报告由此提供一组能够复查的联系：任务要求怎样落实到公开定理，工具反馈怎样接到证明修改，协助成果怎样进入最终代码。对这些联系的检查，使工作流程的改进有具体对象，也使后续效果比较有明确依据。

# How probability proofs are completed

**Authors:** Shuo Deng; Kenneth W. Shum (corresponding author).

*An evaluation of the ProbabilityTheoryFormalization project*

**Revision 26 · 14 September 2026 · Results updated through 14 September 2026**

<a id="abstract"></a>

## Abstract

Large formalization projects require organization beyond an individual proof: AI agents divide work, combine intermediate results and deliver theorems that later proofs can use. ProbabilityTheoryFormalization provides such an environment for a probability textbook. This report combines earlier reviews and corresponding code revisions with two batches of three configurations on eleven task groups to evaluate how the project supports proof development. [[1,4-12,24,41]](#ref-1)

The experiment compares the prescribed project workflow (A), a Sol author that can consult project references and call assistants (B), and Astra coordination of Sol authors and checking services (C). Under a common mathematical-outcome criterion, A and B complete 10/11 groups and C completes 11/11 in the first batch; all three complete 11/11 in the second. Three second-batch rejections originally concerned a modular interface, a prescribed proof route and a derivable premise. Code inspection and caller checks support the revised outcome assessment. A has the highest median solving time in both batches without a corresponding coverage advantage. Results are reported by batch, with changes in instructions and execution arrangements explained. [[13,14,38,41,42]](#ref-13)

The trajectories show how proofs and deliveries were completed. Review prompted a derivation of centered moments from raw moments, and an assistant's inversion proof entered uniqueness and subsequent applications. Old Scheffe deliveries left an eventual-integrability scope gap: explicit scope instructions made the diagnostic reviews consistently require repair, and both separate repair runs passed acceptance. Historical cases trace density derivation from a probability model, assembly of compatible local limits and caller migration. Increasing historical acceptance and changes in the composition of later revisions are examined separately. [[4-11,17-20,25,27,43]](#ref-4)

The second-batch process analysis covers all 33 runs, with 4,054 actual tool calls (excluding 179 tool-discovery calls) and 66 fixed-start records. It identifies interface adaptations between retrieval and proof, breaks in delivery of local work, and recurring tool problems that motivate validated startup-information and parameter-checking prototypes. [[45,46]](#ref-45)

These results support concrete improvements: review the final theorem's mathematical scope, make intermediate work available for integration, and assess equivalent implementations consistently alongside their costs. The project's value is demonstrated through these inspectable mathematical achievements and organizational processes. [[21-23,40,42,43]](#ref-21)

**Reading guide.** [Section 1](#section-1) introduces the project and questions, [Section 2](#section-2) explains evaluation, and [Section 3](#section-3) reports outcomes and resources. [Section 4](#section-4) explains problems of scope, proof construction, and delivery; [Section 5](#section-5) follows retrieval, revision, and actual use in the second batch; [Section 6](#section-6) discusses workflow design. Complete cases and historical analyses remain in [Appendix R](appendix.en.md#appendix-r); methods and individual records for the new analysis are in [Appendix S](appendix.en.md#appendix-s).

<a id="section-1"></a>

## 1 How the project organizes and maintains proofs

<a id="evaluation-questions"></a>

ProbabilityTheoryFormalization is the object of this evaluation: a project for turning textbook mathematics into proofs that can be reviewed, used by later tasks and maintained as dependencies change. A successful build, a passing opinion and a completed textbook task are related but different accomplishments. The report asks three questions:

1. **What mathematics has been completed and made usable?** Does the public theorem express the intended claim, discharge its required proof work and connect to the results and callers on which its use depends?
2. **How do review, assistance and control affect the work?** Which observed decisions repair proofs, validate existing work, leave a scope gap or interrupt delivery, and what information was available when those decisions were made?
3. **How trustworthy are the completion and progress judgments?** Which records refer to distinct opinions and comparable mathematical objects, and what do the resulting labels, code checks and resource measurements actually establish?

Historical reviews and code revisions, and the A/B/C task comparison, answer different parts of these questions. Their relationship is set out in [Section 2](#section-2); they are not combined into one completion rate. This section first explains the documented project design. Evidence of its actual mathematical work, operating failures and maintenance comes from the dated studies that follow, rather than from the presence of a component in the design alone. [[1,4-12,26,34,35]](#ref-1)

<a id="section-1-1"></a>

### 1.1 From a probability textbook to a formal proof library

[ProbabilityTheoryFormalization](https://github.com/Kind-NK-Hill/ProbabilityTheoryFormalization), formerly ToyApollo, develops AI-assisted formalization of a probability textbook. Its goal is to turn textbook definitions, statements and arguments into Lean declarations and proofs that express the intended mathematics and can be used by later chapters. Lean checks the formal proofs; Mathlib supplies the general mathematical library available to them. [[26,34]](#ref-26)

Work begins with the textbook material. The supplied text is organized into numbered subsections or exercise sections. A task plan identifies the statements to formalize and the earlier results they may use, including explicit references in the textbook. The program assembles the source, requirements, permitted dependencies and working draft into a task package for the author. During implementation, the author may search the allowed library and develop additional supporting lemmas. [[34,35]](#ref-34)

The project separates mathematical decisions from software checks. AI agents choose proof routes, write code and assess mathematical correspondence. Python programs prepare tasks, invoke checks and enforce conditions for accepting code. Lean checks the code, while SQLite records task status and retained build and review evidence. Drafts are kept separately from the **canonical corpus**, the project's official Lean proof library. Project acceptance brings reviewed work into that library. [[34]](#ref-34)

In this report, an **agent** is an AI execution session in Codex, with a configured model, conversation context and tools. An **author** writes proofs; a **helper** supplies code or mathematical analysis; a **reviewer** checks statements and proofs. These are AI roles, rather than the human authors of this report.

<a id="section-1-2"></a>

### 1.2 Writing, reviewing and accepting a proof

The program gives an AI author the textbook source, task requirements and permitted earlier results. The author writes Lean code and checks it with Lean. A separate AI reviewer then assesses whether the formal statement and proof satisfy the source and task requirements. Work needing correction returns for repair or diagnosis. Before reviewed code enters the official proof library, the program checks that the passing review still applies to the code and materials being accepted. This is the documented process; the later cases show where actual execution diverged. [[34,35]](#ref-34)

Lean and the AI reviewer answer different questions. Lean checks a proof against its formal statement. **Semantic review** asks whether that statement expresses the required mathematics, whether essential proof work has been completed rather than assumed, and whether listed callers can use the result correctly. A passing Lean check alone cannot establish correspondence with the textbook.

| Stage | Responsible actor | Result |
|---|---|---|
| Prepare the task | Program | Source, task requirements, permitted dependencies and a working draft are assembled. |
| Write and check the code | AI author, using search and Lean tools | A candidate proof (the current code version), or diagnostics guiding the next edit. |
| Review the mathematics | Separate AI reviewer, invoked by an agent managing the workflow or by a human operator | An opinion on the statement, proof responsibilities and listed callers. |
| Repair or clarify the problem | AI author; a separate read-only diagnoser when needed | Revised proof code, or a clarified statement and proof route. |
| Accept the reviewed code | Program | A valid review is matched to the current code and requirements; code enters the official library and the operation is recorded. |

An ordinary proof gap, such as a missing lemma in an accepted approach, returns to the author for repair. A mismatch with the source, an essential conclusion hidden in an assumption, or an unclear proof route can instead require a **read-only diagnosis**: an AI diagnoses the problem before proof editing continues. It does not write the proof or replace the reviewer. The workflow also blocks resubmission of an unchanged candidate after a semantic failure. Section 1.4 explains the risk-triggered **Math Gate**, which checks a proposed statement and proof route before authoring proceeds. [[34]](#ref-34)

Request preparation is not the same as execution. For example, `review-now` prepares review material and identifies the next action; an agent managing the workflow or a human operator must still invoke the reviewer. Similarly, helper-produced code must be exported from its workspace and returned to the role that can use it. A completed service call therefore need not mean the author received a usable result. The case analysis checks what was actually returned and read. [[19,34]](#ref-19)

Finally, the program checks that the review concerns the current candidate, auxiliary code, source and requirements. The records call this **review binding**. It prevents an opinion about one version from approving another. If applying the code fails, the prior official file is restored. A failed re-review of an existing official proof normally preserves that code and records a repair need. These checks maintain the relation between a decision and its evidence; they do not make the AI's mathematical judgment infallible, as the L3 case in Appendix R.1.2 shows. [[34,39]](#ref-34)

<a id="section-1-3"></a>

### 1.3 What it means to complete a proof

A **source obligation** is mathematical work required by the task. A **public premise** is an assumption a caller must supply. Moving a required intermediate conclusion into such a premise leaves that proof to the caller. A **candidate** is a particular code version. An earlier project revision illustrates this distinction.

The historical inversion task `thm_9_5`, which connects interval probabilities to integrals of a characteristic function, shows why a valid conditional proof can still leave work unfinished. Its early candidate already contained substitution, pointwise cases, dominated convergence and rescaling. An assumption called `h_spine` supplied three analytical ingredients: integrability, justification for exchanging integrals and the Dirichlet-integral limit. Successive candidates moved those duties into the proof. [[1]](#ref-1)

| Revision stage | Mathematical work already present or added | Work still supplied by the caller |
|---|---|---|
| Initial conditional proof | Main argument conditional on its analytical ingredients | Integrability, integral interchange and the key limit |
| Next candidate | Product integrability from bounds and finite measure | Interchange and the limit |
| Following candidate | Interchange for nonnegative truncation parameters | The Dirichlet-integral limit |
| Completed assembly | Limit from error bounds; previously proved ingredients assembled | `h_spine` removed |

The restriction to nonnegative truncation parameters matters. The final proof sends the parameter to positive infinity, so it does not need the stronger all-parameter auxiliary statement initially planned. Narrowing that internal lemma avoids unnecessary work without weakening the textbook target. Retaining a required ingredient in the public `h_spine` premise, by contrast, leaves real work outside the delivered theorem. Earlier reviews recognized intermediate progress that a sequence of non-pass labels alone would hide. [[1]](#ref-1)

<a id="section-1-4"></a>

### 1.4 Mathematical route checks and task scheduling

A **parent task** owns the original textbook claim. The **Math Gate** checks a natural-language proof route and proposed Lean statement when there is source mismatch, core proof work shifted into public assumptions, or repeated failure without a clear route. Most small tasks do not use it. A `go` permits planned parent-task writing; a `stop` suspends ordinary writing under that plan until the reported issue is addressed. The instruction determines the scope of a pause; the label alone does not establish that all support work is prohibited. [[26,34]](#ref-26)

For multiple tasks, batch planning reads the recorded state and dependencies to distinguish work ready for authoring, work needing review or route checking, and work blocked by an upstream task. It can organize a worker queue around downstream dependencies and potential work conflicts. The plan identifies the next actions; the agent managing the workflow invokes the corresponding roles, and each task still follows its own acceptance path. An empty ordinary-author queue can therefore mean that a reviewer or diagnoser must act next, rather than that all work is finished or the user must intervene. [[34]](#ref-34)

<a id="section-1-5"></a>

### 1.5 Library interfaces and maintenance after acceptance

The same textbook concept can have different Lean representations in the project and in Mathlib. Importing a theorem expressed with the project's expectation, for example, does not by itself convert it into a theorem about a Mathlib integral. For important shared concepts, the documented policy is to introduce the textbook definition and basic properties, prove a **translation theorem** connecting that interface to Mathlib, and then usually use the Mathlib form in later work. This is a policy for recurring mathematical interfaces, not a required cycle for every local lemma. Existing runnable files are kept unless a concrete reuse problem calls for an interface repair. [[35]](#ref-35)

Dependency selection follows actual use. Mentioning expectation in a source passage supplies mathematical context; it does not automatically require importing the project's expectation definition. An import is justified by the declaration, earlier theorem or translation the proof needs, and the dependency trail records that reason. General library infrastructure is legitimate support. If an auxiliary theorem carries the assigned task's mathematical content, however, review must inspect it as part of that task's proof, not exempt it because it is named a bridge. The variance-expansion comparison in [Appendix R.1.1](appendix.en.md#r1-1) and the Gamma/Dirichlet history in [Appendix R.3.1](appendix.en.md#r3-1) examine this distinction in concrete proofs. [[35]](#ref-35)

Acceptance does not end maintenance. A changed definition or theorem signature can require callers to provide different arguments or assumptions. The task and dependency records identify affected work; builds and review check the revised interfaces and their use. SQLite keeps a rebuildable index of the underlying evidence, separating an earlier passing review, coverage of the current code and support, and a working candidate that still needs attention. A change requires the relevant coverage to be checked again, not merely retention of a pass label. The total-variation repair in [Appendix R.3.2](appendix.en.md#r3-2) shows this obligation concretely: the source's probability-measure condition had to reach both the definition and its callers. [[7,34]](#ref-7)

## 2 Evaluation evidence and methods

Two bodies of evidence address the project questions in [Section 1](#evaluation-questions). **Historical reviews and corresponding code revisions** show how proof responsibilities, public statements, shared support and callers changed during the project's development. They also allow the study to reconstruct distinct judgments, qualify comparisons of mathematical targets, examine selection after failure and check saved code beyond its acceptance labels. These analyses have their own questions, methods and findings in [Appendix R.3](appendix.en.md#r3) and Appendices [C](appendix.en.md#appendix-c), [D](appendix.en.md#appendix-d) and [L](appendix.en.md#appendix-l). [[1,4-11,32]](#ref-1)

**The eleven-group A/B/C comparison** examines the project's prescribed workflow alongside two alternative ways of organizing work on the supplied tasks. Deliveries and resource accounts establish what each executed arrangement produced and expended; execution records explain particular repairs, missed checks and interruptions. Sections [2.1–2.4](#section-2-1) specify that comparison, and Sections [3–5](#section-3) report its findings. The experiment does not replace the historical evidence about maintenance, nor does historical acceptance supply additional experimental successes. [[12-14,24,31,38]](#ref-12)

**Trajectory analysis connects work to outcomes in both bodies.** It follows the mathematical duty, the opinion or instruction, the observable response, and the code and delivery subsequently assessed. The available detail differs between historical records and experimental logs; receipt, use or motivation is not supplied where the record cannot establish it. [Section 2.5](#section-2-5) explains the reconstruction and its coverage. The questions organizing this report are separated from the original experimental motivation below and from the retrospective analyses subsequently performed. [[9,10,17-20,24,25,27,29,40]](#ref-9)

<a id="section-2-1"></a>

### 2.1 Why compare A, B and C?

Completing a probability proof requires writing code and deciding when to check it, how to respond to errors and when to submit. The project prescribes review and repair procedures for these decisions. The experiment examines whether those arrangements help agents deliver complete proofs, comparing them with two autonomous alternatives: a Sol lead author organizing its own work, and Astra coordinating Sol authors and checking services. All three work on the same task groups. B and C are experimental alternatives, not later production stages of the project. We compare completion, elapsed solving time and recorded model activity. [[12,14]](#ref-12)

**A follows the prescribed project workflow.** A Sol author chooses proof routes, searches the library and edits code; other Sol sessions perform checks. The workflow sets review and repair requirements and conditions for accepting code into the maintained library.

**B lets the Sol lead author organize the work.** It receives general work guidance, can consult project workflow and review documents, and can request other Sol sessions to help write or review code. The lead author decides how to use these resources, whether to request checks and when to submit. The experiment does not require it to complete A's prescribed sequence.

**C lets Astra organize Sol's work.** The Astra coordinator can read tasks and code, give a Sol author specific mathematical advice or editing instructions, and choose its next action from the author's results and checking feedback. It knows the available services and how to invoke them, but does not receive the full internal checking instructions. Calling checks is its choice; checkers still work under instructions fixed by the backend. [[12,18,38]](#ref-12)

| Configuration | Who organizes the work? | What assistance is available? | How are checks arranged? |
|---|---|---|---|
| A: prescribed workflow | Sol author under project requirements | Project-role instructions and AI checks | Workflow sets review and repair requirements |
| B: Sol-led organization | Sol lead author | Project references; other Sol authors or reviewers | Lead author chooses calls and follow-up |
| C: Astra coordination | Astra coordinator; Sol author implements | Tool descriptions; Sol author and fixed checking services; returned feedback | Coordinator chooses calls and follow-up |

All these roles are AI agents. Sol and Astra denote the recorded `gpt-5.6-sol` and `gpt-6-astra` configurations. Authors and checking roles use Sol; only C's coordinator uses Astra. All use medium reasoning effort: medium names the reasoning setting, not a model-capability tier. B is an autonomous configuration with document access and assistance; the experiment does not include a separate minimal baseline given only the problem without project documents or other-agent help. C changes the decision-making model, role structure and information access together, so the experiment compares three complete arrangements. [[12,18,31]](#ref-12)

Within this comparison, trajectory analysis asks when a prescribed or voluntarily requested check identifies the missing mathematical work, when it incorrectly clears a result, how a coordinator uses returned feedback, and why work continues or stops. For the same task, it first checks whether configurations encounter the same difficulty, then traces who identifies it, whether the opinion arrives and how code changes. Appendix R.1–R.2 use these sequences to explain specific strengths and failures of the executed arrangements, rather than treating the completion totals as a measure of review quality.

### 2.2 What information do agents receive, and how does a task proceed?

Each configuration receives textbook source, task requirements, the permitted mathematical library and designated prior results. Agents must submit theorem statements, proofs, necessary auxiliary code and an explanation of how they meet the task. A **delivery** comprises this code and explanation. [[12]](#ref-12)

An **outer experiment agent**, also an AI agent in Codex, starts and manages a run. A, B or C organizes solving with the supplied materials and time allowance, then delivers its work. Fresh reviewer sessions evaluate the delivery against common criteria. Internal review, acceptance into the project library and experimental acceptance are recorded separately; Section 2.4 explains scoring.

The outer experiment agent and C's Astra coordinator have different responsibilities: the former manages experimental runs, while the latter organizes proof work inside C. The outer agent can intervene in any configuration, for example by stopping further activity. Section 2.3 and individual cases describe these actions and their consequences. [[31,38,39]](#ref-31)

The materials serve different purposes. **Workflow documents** explain how the project organizes writing, review and repair. **Review documents** explain what checks should address, such as extra assumptions or missing parts of the required conclusion. **Tool descriptions** explain which services can be requested and how to invoke them. **Checking feedback** identifies problems in the current code or gives a passing opinion.

A's authors and checkers receive their respective project-role instructions. B's initial prompt gives general advice to plan, search, check and seek help as needed; workflow and review references are available for active consultation. Availability does not establish that a particular run reads them. C's coordinator can read public tasks, code and feedback, but does not receive the full internal general-review and mathematical-check instructions. Feedback may nevertheless reveal some criteria. C therefore chooses how to organize work; the coordinator does not freely set the task requirements or the backend's checking instructions. [[38,39]](#ref-38)

B's lead author can operate a terminal, edit code and compose requests to other Sol sessions. C separates coordination from execution: Astra reads code, assigns authors and requests checks through tools; the Sol author operates a terminal and edits code. The coordinator can give specific proof advice, but cannot rewrite a checker's internal instructions through the fixed checking tools. Both configurations' internal reviews are part of solving; common experimental evaluation follows submission. [[38,39]](#ref-38)

The experiment selects eleven groups covering different mathematical work and organizational questions. Some groups require several connected results. ### 2.4 Completion evidence and post-submission common evaluation

Calling an experimental task complete requires a judgment about the delivered mathematical scope, not just a successful command or the author's decision to submit. Lean checks the statement actually written; a semantic reviewer assesses its relation to the task; project application validates the review's correspondence and eligibility before accepting code. For the task comparison, separate post-submission reviewers make the reported completion judgment under the common procedure below. The following evidence types therefore answer different questions:

| Evidence | Question it answers |
|---|---|
| Build | Does the written code check in the recorded environment? |
| Semantic review | Does the reviewer judge the statement and proof to meet the source obligations? |
| Binding and production acceptance | Has the project applied an eligible review to the required code and current review basis? |
| Post-submission common evaluation | Does the experimental delivery meet the criteria adopted for this experiment? |

Section 3 uses a common mathematical-outcome criterion across both batches: the delivery must cover the full target, allowing equivalent routes and composable interfaces. Independent caller checks verify redundant parameters directly entailed by the original assumptions and permitted library. Compliance with a prescribed route is recorded separately. Original common reviews supply existing evidence; subsequent reconciliation corrects inconsistent judgments while retaining those reviews. The original review procedure follows below; [Appendix Q.2](appendix.en.md#q2) gives the reconciliation rules and three changes across 66 items. Historical records retain their dated meanings, and experimental completion remains distinct from production acceptance. [[13,26,42]](#ref-13)

**Common evaluation** is the experiment's assessment after submission, separate from help and internal review during solving and from production acceptance. The original endpoint procedure requested two fresh, read-only semantic opinions on the source, task, candidate, permitted upstream material and recorded technical checks. Configuration metadata was withheld from the evaluator-facing request. Matching pass or fail votes completed the decision; two inconclusive votes left it unresolved. Different votes triggered at most one fresh adjudicator, who read the same materials and the two opinions and resolved their substantive disagreement rather than choosing by confidence. All original, consistency and targeted endpoint calls use the recorded Sol medium configuration. [[30]](#ref-30); [Appendix N.6](appendix.en.md#n6)

A group decision concerns the required complete delivery. Passing the coordinate-convergence theorem alone does not complete the two-target vector-convergence group, and a verdict on explicitly partial material describes that material rather than the missing task. Invalid result formatting is also separated from mathematics. In the representation-theorem case, a reviewer wrote a pass but used an object where confidence had to be a number; the evaluation software recorded an inconclusive execution result and the procedure proceeded to adjudication. [[22,28,30]](#ref-22)

Reassessment then examined inconsistent interpretations in variance expansion, Scheffé's lemma and Cauchy scope. Each candidate received separate initial opinions under the stated readings. A necessary adjudication could be triggered by disagreement on an obligation, an invalid result, or inconsistent treatment of corresponding behavior across candidates. These adjudicators could see the new initial opinions and a cross-candidate consistency summary; they were not blind to that later evidence. For the inversion group, the original submission explanations were supplied symmetrically after the six initial reviews, when the anonymous code-only view proved insufficient for a documentation judgment. [[23,30]](#ref-23)

The corrected acceptance for the 12 September comparison adopted four explicit readings: permitted general expansion for variance additivity, the task's eventual-tail formulation for Scheffé, the textbook's standard-Cauchy core, and reasonable disclosed repairs of the deficient continuous-mapping assumptions. At 09:22 on 12 September, existing opinions were reused, determinable format mismatches were repaired and outcomes were recomposed under those criteria. The two additional continuous-mapping opinions had already been obtained in the 05:17 supplement. This was a retrospective criterion correction, not new solver work. [Appendix R.1](appendix.en.md#r1) gives its mathematical basis and retains the original outcomes. [[13,15,22,30]](#ref-13)

[Appendix N.6](appendix.en.md#n6) states the stage-specific rules, evaluation inputs and masking limits. Here **independent** means the documented separation of reviewer sessions and roles; adjudicators deliberately receive earlier evidence, and using separate sessions of the same model does not establish independent model errors.

The 13 September A-L7 continuation is a separate delivery and assessment. Its two fresh evaluations distinguish correctness of the disclosed repaired statement from literal compliance with the original statement. Appendix R.2.6 and [Appendix O.2](appendix.en.md#o2) report that outcome and its additional resources; the completed continuation is included in Section 3.1. [[39]](#ref-39)

### 2.5 Following information, decisions and proof changes

Trajectory analysis asks how a task reaches its result. For each focal case, we connect the mathematical requirement, information actually received by the author or coordinator, the next action, changes to the declaration and proof, and the version eventually assessed. Historical cases use the same questions across reviews and code revisions, with additional checks that the earlier and later records concern comparable mathematical targets. [[8-11,17-20,25,27,29]](#ref-8)

The central comparison is between the work before and after a consequential event. A review may lead to a new derivation, support submission of unchanged code, or fail to reach the author. A helper may produce a valid proof that never enters the delivered result. We inspect tool returns and reading records, compare code, and follow actual calls to reused results to distinguish these processes. When a link cannot be recovered, its contribution remains unconfirmed; the observed sequence can still explain the work around it. [Appendix R.2](appendix.en.md#r2) presents those findings. [[17-20,24,25,27,40]](#ref-17)

The cases were selected from investigated repairs, assistance and execution problems. They support explanations of particular processes. Broad log extraction covers all recorded solving runs, but assessing the correctness and use of feedback requires further reading. A separate assessment applies the same detailed criteria to six of 127 indexed internal services; the other case studies have their own documented scope. These sources do not establish an overall rate of correct-feedback adoption or mathematical repair. [Appendix N.4](appendix.en.md#n4) gives the units and coverage, [G.18](appendix.en.md#g18) gives the six assessments, and [M.2](appendix.en.md#m2) gives log-processing rules. [[16,24]](#ref-16)

A separate study reviews each of two fixed old L3 candidates under the original instruction and an explicit tail requirement, with three fresh reviews per condition: 12 in total. Each old candidate also receives one explicitly directed repair. Diagnostic code and repair instructions are separately frozen; these runs are separate from the 33 main runs. Appendix R.1.6 reports the results and [Appendix Q.4](appendix.en.md#q4) provides inputs and decisions. [[43]](#ref-43)

A further analysis covers all 33 second-batch runs using the same starting-point rules: the earliest mathematical retrieval and the earliest proof or interface diagnostic in each run, followed through later actions, local results and final code. This yields 66 records. The starts concern the same need in 25 runs and are summarized separately. Chapter 5 reports this analysis; selection rules, per-run records and reviews appear in [Appendix S](appendix.en.md#appendix-s). [[45]](#ref-45)

Unavailable commands occur in all 33 selected first-batch runs, and file-access problems in 27. ### 3.4 Model usage and solving time

## 4 Problems encountered between starting a proof and completing a task

Section 3 shows that all three configurations completed every second-batch task, with different times. To understand those results, we examine the work performed along the way. This section introduces eight kinds of problem in the order in which proof work develops, using existing cases to explain their consequences for delivery. Section 5 then applies a common analysis to second-batch retrieval, diagnostics, and code use.

<a id="section-4-1"></a>

### 4.1 Establish the required scope and check the delivered result

**Establishing scope.** The textbook statement, task instructions, and library assumptions must be aligned. The author needs to identify which inputs the task covers, which properties must be derived within the proof, and which generalizations are additional work. These decisions determine the required delivery. [Appendix R.1](appendix.en.md#r1) preserves the mathematical grounds for the individual judgments.

The first-batch Scheffé task (L3) shows why scope changes the completion result. The old A and B deliveries required every function in the sequence to be integrable. The task also covered sequences integrable from some point onward. Such an input permits finitely many initial terms to be nonintegrable and therefore cannot be passed directly to the old theorem. Completing the task requires selecting an integrable tail, applying the argument there, and transferring the limiting conclusion back to the original sequence. The missing work is a proof step needed to cover the required inputs. [Appendix R.1.2](appendix.en.md#r1-2)

**Checking the final delivery.** Reviewers must examine the same scope. In new reviews of the two fixed old candidates, all three A reviews and two B reviews passed under the original instructions. After an explicit request to check the tail requirement, all three reviews of each candidate required repair. All three original-instruction B reviews had discussed the scope issue, but two treated it as an optional generalization. Recognizing a problem and making it an acceptance requirement were separate decisions in these records.

Two separately conducted targeted repairs subsequently added the tail interfaces and passed common acceptance. The repairs show that these gaps can be resolved under explicit requirements; the fixed-code diagnostic reviews show what reviewers noticed and required. [Appendix R.1.6](appendix.en.md#r1-6) and [Q.4](appendix.en.md#q4) preserve all twelve opinions, the repair instructions, and the code changes. These separate repairs retain their own results; the original first-batch deliveries remain scored against their recorded code. [[43]](#ref-43)

<a id="section-4-2"></a>

### 4.2 Find mathematical tools and assemble the proof

**Finding material.** An author may know the mathematical result needed without knowing its library name or location. Keyword searches, source reading, and declaration-type queries identify candidates; empty results or unknown names may require a revised query. The first observable advance is the material found. [Appendix R.2.1](appendix.en.md#r2-1)

**Connecting declarations.** A candidate theorem's inputs and output must fit the current goal. Index conventions, function representations, type conversions, and measurability or integrability assumptions can require additional work. Even declarations expressing the same mathematical relation may need a connecting proof before they can be composed. Section 5.2 examines such a conversion in detail.

**Completing the mathematical argument.** When existing results supply only part of the work, the author must establish auxiliary lemmas and assemble them. In the first-batch fourth-moment strong-law task (A-M2), this included deriving the central-moment bound needed later in the proof from the raw fourth-moment assumption. Following feedback, the author added the derivation and moved a condition previously left to the caller into the proof. The case identifies the mathematical work actually completed. [Appendix R.2.2](appendix.en.md#r2-2) gives the before-and-after code and checks. [[25]](#ref-25)

**Assessing and acting on feedback.** Build output locates problems in formal code, while mathematical review examines the task and proof content. The author must assess the opinion against the current version and then edit, search further, change route, or request assistance. Connecting these steps establishes what happened after the feedback. [Appendix R.2.8](appendix.en.md#r2-8)

<a id="section-4-3"></a>

### 4.3 Deliver work and enable its continuation

**Delivering assistance.** A helper may prove one lemma or implement an entire task group. The author continuing the work needs readable code, integration, and a checked call to the result. In the first-batch inversion task (H1), the helper's result was used in uniqueness and subsequent applications. Other assistance produced code whose use in the final proof was not confirmed. Assessing adoption requires the returned material, code changes, and call sites. [Appendix R.2.3–R.2.5](appendix.en.md#r2-3) preserves these comparisons. [[17-19,28]](#ref-17)

**Resuming execution.** File access, command entry points, result transfer, and external stop instructions can interrupt proof work. The agent must use the actual response to identify a possible next action. First-batch A-L7 completed review and delivery after continuation was authorized; its trajectory involved both a statement correction and restored permission to work. Both conditions are needed to interpret the result. [Appendix R.2.6](appendix.en.md#r2-6) gives the states before and after continuation. [[39]](#ref-39)

These problems connect the final result to intermediate work: retrieved material must fit the goal, local proofs must reach their users, and the delivery must cover the required scope. The next section follows those connections in the second-batch records, reporting the common tracking results before examining individual trajectories.

<a id="section-5"></a>

## 5 From retrieval and revision to actual use

All 33 second-batch runs passed common mathematical acceptance. Beneath that shared outcome, agents searched, tried declarations, revised code, and collaborated. This section follows how that work connects to the final proof. It asks how retrieved material became usable, what happened after diagnostic feedback, and how local results reached the final delivery.

<a id="section-5-1"></a>

### 5.1 Follow the work on the same proof need

The analysis begins with the complete tool records for three configurations on 11 task groups. Pairing and deduplication yielded 4,054 actual tool calls, alongside 179 tool discoveries. The records preserve inputs and responses. A call can combine search, editing, and checking, so its contents must also be read to establish the particular proof need addressed. [[45]](#ref-45)

Each run contributes two starting points: its first active search for a mathematical name, type, or source, and its first proof or interface diagnostic after the source file has loaded. Subsequent queries, code changes, and checks are followed for the same need, with a separate examination of final source. Starting from a theorem search, for example, the later record should establish whether the candidate applied, what connection the author supplied, and whether related work was ultimately used.

| Material examined | Coverage | Question addressed here |
|---|---:|---|
| Actual tool calls | 4,054 | Which operations and responses occurred, and where tool problems appeared |
| First mathematical retrieval and its continuation | 33 | How work after retrieval advanced the proof and connected to final source |
| First proof or interface diagnostic and its continuation | 33 | What the check exposed and how the same need was subsequently handled |

The two starting points yield 66 records. In 25 runs they concern the same need, so the cohorts are summarized separately. This rule covers early work in every run; later, newly arising searches and repairs have not all been individually annotated. The counts below describe the selected processes. Finding a related declaration, passing a local check, and use in final source are recorded separately. [Appendix S.1–S.3](appendix.en.md#s1) specifies selection and review responsibilities.

<a id="section-5-2"></a>

### 5.2 What work remains after a relevant theorem is found?

The table records the connection between the 33 retrieval records and final source. Tracking follows the need addressed by the first retrieval through later searches and edits. It describes where that work led and cannot be read as a first-query hit rate.

| Connection between the followed process and final source | Records |
|---|---:|
| At least one related declaration explicitly used | 29 |
| Related implementation or partial work retained | 2 |
| First helper's work replaced by a later delivery | 1 |
| Connection not established | 1 |
| Total | 33 |

The table establishes connections between retrieval and delivery; the code explains how those connections were made. The quantile construction in second-batch Skorokhod task B-M3 provides a concrete trajectory. The author found tools for distribution-function limits, monotonicity, and right continuity. The textbook and library definitions, however, represented the function differently. Relevant mathematical results had been found, but direct rewriting still failed type checking.

| Stage | Recorded action or result |
|---|---|
| Retrieval and trial | Related distribution-function tools were found and tried with the current definition |
| Diagnostic feedback | Direct rewriting failed because the function representation did not fit the declaration being used |
| Proof revision | Pointwise equality between the definitions was proved, promoted to function equality, and used to rewrite the goal |
| Checking the result | The support file passed its check, and final source retained the conversion |

The revision addressed a specific object: connecting the two representations so that the existing theorem could apply to the current goal. Reading only the retrieval response would omit the proof needed before application. Reading only the final pass would hide why the conversion appeared. Tool responses, revised code, and the final call jointly explain the advance. [Appendix S.2–S.3](appendix.en.md#s2) preserves the individual evidence.

Second-batch stopped-process task B-M1 shows how related work crossed roles. A reviewer searched and returned a stopped-process interface with a concrete route for composing the martingale result. The author received that material, reread the source, supplied definition bridges, corrected index conversions, and called the route in the final proof. Both delivery of the material and subsequent use can be confirmed; the intervening definition and index work identifies the adaptation still required from the author.

These cases make the work after retrieval an observable part of proof construction. The records establish the connections described above. Recorded progress endpoints have different depths, so they do not support comparisons of overall recovery rates or recovery speed between the three configurations.

<a id="section-5-3"></a>

### 5.3 What changed after the diagnostic?

Of the first proof or interface diagnostics, 19 arose in implementation and 14 in temporary declaration queries or local experiments. The distinction helps interpret a response. An error in a developing proof calls for checking how that goal was repaired. A library-name probe can return the type of a useful declaration alongside messages that other names do not exist.

A process must therefore be read around a specific object. In B-M3, the edits addressed the same function-representation problem, and later checks and source establish its resolution. In second-batch linear minimum mean-square error task B-L6, one squared-integral experiment had no observed resolution, while the overall task subsequently passed common acceptance. Recording the task outcome and the experiment's outcome separately preserves what happened to the intermediate work.

This also explains the relationship between the error counts in Section 3.3 and the present analysis. Error distributions identify runs that generated the relevant feedback; subsequent actions explain how the agent handled it. Neither the number of errors in a response nor the final task result alone establishes how a particular proof need was resolved. [Appendix S.2](appendix.en.md#s2) provides the complete per-record tracking table.

<a id="section-5-4"></a>

### 5.4 How does locally checked code reach the author?

Work across roles has a separate delivery step: a proof in a helper's workspace must actually return. In second-batch A-M2 and A-M3, the first helper had code that passed a local check but returned an empty patch. When the author subsequently read its own file, it still contained the task input. The local proof had advanced, but the file available to the author had not changed accordingly.

| Location checked | Observed state in A-M2 and A-M3 |
|---|---|
| Helper's workspace | Code had passed a local check |
| First return | The patch was empty |
| Author's subsequent file read | The file still contained the task input |
| Later work | Renewed delegation and delivery brought a nonempty patch into the author's workspace |

This record locates the break in transfer. The eventual task pass cannot supply code absent from the first empty return; later deliveries retain their own provenance. In B-M1, by comparison, returned content and the final call establish actual use. Together the trajectories show why examining collaboration requires the helper's work, the actual return, and the recipient's file. [Appendix S.3](appendix.en.md#s3) provides patch contents, file correspondences, and source references.

The usefulness of assistance thus has concrete checks: what the author received and which material entered the subsequent proof. These cases establish connections or breaks at those locations. They do not measure time saved by assistance relative to working alone.

<a id="section-5-5"></a>

### 5.5 Turn tool problems into a testable improvement

The preceding sections follow particular proof needs. Here the analysis returns to all tool calls to examine execution problems across runs. Command lookup failed in 173 calls; 49 still had an outer exit code of 0. Identification uses the actual command response because the outer status does not fully describe internal execution.

Of these calls, 66 attempted to invoke `apply_patch`, spread across all 33 runs and 64 sessions. The same issue across sessions motivates explaining the available command entry points when work begins. Lookup failure can also arise from names or search paths; [Appendix S.4](appendix.en.md#s4) gives the categories and sources.

A startup tool-information card was implemented on this basis. A separate parameter preflight check addresses rejected tool parameters. Each prototype targets a defined problem and received its own functional validation. [[46]](#ref-46)

| Prototype | Problem addressed | Validation completed |
|---|---|---|
| Startup tool-information card | Make actual tool entry points visible to the author at the start of work | An isolated container check covered default entry points and a changed search path, confirming that the card distinguishes those states |
| Parameter preflight check | Identify invalid parameter formats or values before execution | Static replay of 3,896 inputs to two tools identified 9 original rejections and accepted 3,887 valid inputs, matching the original program's parameter conditions |

These results establish prototype function. Valid parameters may still encounter execution problems, and whether agents change their actions after receiving correct information remains an empirical question. The proposed follow-up changes only the startup card, holding tasks, starting states, budgets, roles, and mathematical criteria fixed. Parameter preflight serves as a common offline checker for both groups. This model-effect comparison has not yet run.

The findings in this section are concrete: representation changes after retrieval connected material to a proof; empty patches temporarily separated local work from the author's file; and command problems across sessions identified an implementable improvement. They show why evaluation of a workflow needs to connect final mathematical results to the process that produced them.

## 6 Discussion: organizing mathematical work

The preceding results explain the project from three perspectives: Section 3 compares deliveries and resources, Section 4 establishes task scope and kinds of work, and Section 5 follows material, feedback, and code into proofs. This section uses those results to discuss review, collaboration, and the evidence they provide for workflow design.

<a id="section-6-1"></a>

### 6.1 Read completion and resources together

All three configurations delivered stopped-expectation results, the fourth-moment strong law, Skorokhod representation, and the chain from inversion to uniqueness. These tasks include auxiliary lemmas, composition, and adaptation at call sites. Common evaluation across the two batches further shows that C covered every first-batch task while A and B each left an L3 gap; all three completed the second batch.

A had the higher median solving time in both batches without a corresponding coverage advantage. This gives a reason to examine the resources used by the prescribed workflow. Matched tasks also show that the configuration with a lower median was not faster on every task: B and C led on different second-batch groups. Section 3 preserves those differences through per-task results and complete timing. Some prompts and execution arrangements changed between batches, and configurations also combine model and organizational differences. The results do not determine the speed effect of one isolated mechanism. [[41,42]](#ref-41)

<a id="section-6-2"></a>

### 6.2 Locate the contribution of review and collaboration in the work

Review can be examined through changes in missing work. First-batch A-M2 supplied a central-moment bound after feedback. The old L3 diagnostics show that a scope issue can be missed or recognized without being treated as a required repair. The two completed repairs under explicit requirements add code evidence. The processes in Section 4.1–4.2 connect opinion content, acceptance decisions, and actual revision. [[25,43]](#ref-25)

Collaboration also depends on transfer and integration. Second-batch B-M1 connects material returned by a reviewer, the author's definition and index work, and the final call. The empty patches in A-M2 and A-M3 show that a helper may pass its local check while the author still lacks the code. The comparisons in Sections 5.2 and 5.4 locate the affected step. [[45]](#ref-45)

These observations support clear design priorities: review must check the scope required by the task, and assistance must return material the author can use to continue. Whether additional reviews or more helpers improve overall performance still requires comparison of actual outcomes and resources under common conditions.

<a id="section-6-3"></a>

### 6.3 How historical progress complements the present process analysis


Project history spans multiple code versions and adds mathematical progress beyond a single run. Existing investigations trace density derivation from normalized Gamma variables, composition of local limits, and connection of a general central limit theorem to a concrete application. [Appendix R.3.1–R.3.3](appendix.en.md#r3-1) preserves the derivations and caller changes. They explain how the library gradually acquired usable results. [[4-8]](#ref-4)

Historical statistics also examine how to interpret changes in pass counts. Passes still increased after requiring comparable mathematical targets and opinions attached to the correct code, although closely read cases explained only part of that increase. When the proportion of later revisions passing declined, the composition of the followed tasks also changed: the remaining tasks had lower success at the first step. The decline alone therefore did not establish diminishing returns to continued revision. [Appendix R.3.5–R.3.6](appendix.en.md#r3-5) preserves the comparisons and calculations. [[10,32]](#ref-10)

The second-batch analysis supplies a different coverage pattern: it follows two specified starts in every run under a common rule. This adds records of retrieval and use across runs while retaining the concrete code changes presented in Section 5. Historical cases explain longer proof development; common-start analysis shows how selected processes appear across runs. Their counts retain their respective scopes.

<a id="section-6-4"></a>

### 6.4 Develop improvements from observed problems

Supported targets for improvement include making review cover the public theorem's required scope, returning readable and usable code from assistance, and providing accurate tool entry-point information when work begins. The first two correspond to the delivery processes in Sections 4–5; the last has a functionally validated prototype. Evaluation of these changes should retain common mathematical outcome criteria and include waiting, repairs, and assistance within solving resources.

The report thus provides checkable connections between task requirements and public theorems, between tool feedback and proof revision, and between assistance and final code. Examining those connections identifies concrete improvements to the workflow and a clear basis for subsequent effect comparisons.

### S.2 Two fixed starts per run

Each run contributes its earliest proof or interface diagnostic and its earliest active retrieval for a concrete mathematical need, ordered by actual event time. A diagnostic must concern types, names, syntax, instances, or proof goals after source loading. Missing inputs, module-loading failures, and tools that never start are recorded separately as preparation problems. Retrieval requires an actively chosen keyword, declaration type, or source passage; prescribed bulk reading of upstream inputs does not automatically qualify. Development review narrowed the diagnostic rule to v1.1; the earlier version remains available. This is a retrospective design, documented in the [annotation protocol](../research/semantic/PROTOCOL.zh-CN.md).

Annotations connect searches, edits, checks, and handoffs around an identifiable need. A shared filename, session, or arbitrary later passing check does not establish continuity. Cross-role connections require dispatch, return, and candidate evidence. The two starts concern the same need in 25 runs. Accordingly, 66 start records form two sets of 33; the records must not be added as independent recoveries. This fixed-first selection covers early processes in every run rather than enumerating all retrieval and recovery episodes.

Among processes followed from first retrieval, 29 have at least one related declaration explicitly used in final source, 2 have source presence only, 1 was replaced, and 1 remains unknown. ### S.3 Review and evidence

Automatic classification supplies coarse candidates for retrieval, editing, and checking. Review reads actual inputs and necessary output context, accounting for standard-input checks, separate targets within compound commands, replayed warnings, and a successful build followed by an unrelated command failure. Same-file check sequences aid navigation; they are not recovery labels. All 13 real-event regression cases and 5 synthetic boundary cases passed. These are targeted program checks, not a population accuracy estimate; see the [regression results](../research/review/code_audit/regression_results.json).

The 44 records for A and C received non-blind review by other agents. The principal investigator reviewed all 22 B records and requested supplementary checks; the results were then consolidated into 66 adjudicated records. Initial labels, reviews, and changes are preserved separately. All assessors were model agents; there was no human-expert reference set or unbiased accuracy estimate. Review focused on first eligible events, continuity of need, and final-source evidence, rather than inferring adoption from imports or name occurrences.

A-M2 and A-M3 distinguish local success from delivery. Their first support actors obtained passing local checks, but their returns contained empty patches, no applied patch, and empty artifact lists. When the authors later inspected their drafts, these still contained 200 and 65 lines of input material respectively. Subsequent delegation produced verifiable nonempty patches and copies into author files; A-M2 also had an intervening export failure. Its first candidate was ultimately replaced. In A-M3, the first support candidate was replaced, while the author's earlier retrieval process could still be connected to later use. The [A review records](../research/semantic/review_A.json) supply calls, file digests, and original line references.

B-M3 illustrates a connected process. The author searched for distribution-function and quantile resources, expanded the query, and delegated support implementation. The support actor encountered mismatches between the project's distribution function and the library expression; direct conversion still failed. Establishing equality of the two functions then enabled rewriting the limit, monotonicity, and continuity goals, and the support file passed. Final source retained this bridge and the quantile inverse-image result. This establishes local application and use without treating that stage as completion of the entire representation theorem. The two B-M3 [adjudicated records](../research/semantic/adjudicated_annotations.json) identify the chain and final source locations. The [event index](../research/extraction/events.jsonl) contains requests, responses, and their original file and line references, cross-referenced by the [source manifest](../research/extraction/source_manifest.json).

### S.4 Environment observations, prototype checks, and time

Actual error output explicitly reported command lookup failure in 173 calls across all 33 runs; 49 nevertheless had a zero outer exit code. Multiple such messages in one call count once, while command categories can overlap. Lookup failures for `apply_patch` appeared in 66 calls across 33 runs and 64 sessions. Outer success therefore cannot replace reading subcommand feedback, and recurrence across runs does not establish persistent disregard within one session. Lookup failures require attention to paths and spelling; for example, a failed `lake` lookup does not establish that the image lacked the installed tool. These observations describe command lookup failures, not every environment fault or a measured time penalty; see the [environment summary](../research/analysis/environment_summary.json).

An isolated research prototype provides startup tool information and argument validation without changing production. An isolated environment probe checked tool availability. Static replay covered 3,896 historical calls: it rejected the 9 invalid under the original rules and accepted the other 3,887, agreeing with the original argument guards. Another 29 synthetic boundary checks passed. Replay executed no historical commands; valid arguments do not imply execution or mathematical success. The [prototype account](../research/interventions/README.zh-CN.md) and [replay summary](../research/interventions/argument_replay/summary.json) document these checks. No model-effect comparison has been run, so these results establish neither fewer agent errors nor a speed improvement.
