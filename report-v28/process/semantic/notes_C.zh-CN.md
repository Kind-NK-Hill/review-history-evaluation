## 后续推进和最终采用的边界

1. **局部通过的范围跟随当时源码。**M2 第一次干净检查发生时，目标路径虽然已经叫 thm_11_7，文件只包含中心化辅助引理；主强大数律仍在后续添加。M3 第一次通过也只是分位数构造的当时版本。两者都不能写成完整题组已在该时刻解决。
2. **旧探针不自动恢复。**L2 的 covariance_eq_integral 在旧 Check.lean 后续仍报未知名称。实现使用的是 covariance_eq_sub 等现有声明。本条记“接口替代”，没有把后来另一目标通过当成旧探针通过。
3. **同路径可更换内容和义务。**L4 在 thm_8_6 路径先运行包含积分、级数、泊松名称的 #check 清单，后改写成真实证明。后来总变差积分证明通过，只支持该子需求推进，不支持整批接口全部修复。因此首诊断条目整体最终采用记 unknown；检索条目只对已核对的 integral_add_compl 给出明确采用。
4. **精确引用才支持采用。**检索条目的明确采用来自最终证明中的函数应用、`rw`、`using` 或特定重写声明及其检索证据。没有根据导入一整个模块就宣称结果被用到，也没有用自动化策略环境中名称可见推断其实际贡献。即使明确出现，仍不声称该次搜索是最终成功的因果必要条件。
5. **移动源码需要连接证据。**L7 最终 thm_10_10 入口只导入支持文件。标注使用协调者的重组指令 `call_PMduvHuEBhgdyavQZRDs6nSk`、实际移动 `call_8Vll7nVXG7LcmOJ4xES6yj6M` 和最终 coordinate_convergence_support 中相应证明体相连，没有由入口导入单独推断采用。
6. **完整命令的退出码不是所有子步骤的结论。**H1 在 Lean 与目标构建通过后 git diff 报错，不能把已确认通过改成失败。M2 的 `call_ExVWGcVCpc4YCVVnz3F8Tnz3` 把 Lean 输出送入 head，退出 0 但仍可见类型错误，不能当作通过。L6 单独代数试验通过也不是目标文件通过。
7. **先后发生不等于同一恢复。**动作表选的是可由查询目标、源码变更和实际诊断连接的步骤。它不是两时间点之间所有调用的列表。并行其它作者、其它义务、工具说明或旧警告重放不归到该需求。
